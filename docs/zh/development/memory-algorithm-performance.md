## 结论

可以在保持评分公式、阈值、遍历预算、过期内容降权和事务提交规则的前提下继续优化。
本次主要消除了重复读取、重复评分、无必要的全量排序和逐行 SQL 编译。没有引入
近似向量检索，也没有用缩减候选数量的方式牺牲召回质量。

不能把这理解为所有路径都达到“绝对最优”：精确向量匹配仍需扫描向量，实体与
子串未命中仍可能扫描全库，持久化和图密度也有实际成本。报告区分了复杂度下降、
常数优化和未改变的成本。

## N=1、10、100 的验证

N 表示活跃记录数，不是重复运行次数。以下是单次操作的 **CPU 微秒**，格式为
“优化前 → 优化后”，取 5 轮中位数。

| 路径 | N=1 | N=10 | N=100 |
|---|---:|---:|---:|
| 关键词检索 | 4.2 → 3.4 | 37.8 → 30.4 | 355.8 → 290.2 |
| 混合召回 | 78.2 → 75.6 | 919.5 → 283.5 | 6,144.7 → 2,253.8 |
| WHY 召回 | 43.7 → 42.0 | 1,121.4 → 344.5 | 7,561.7 → 2,357.0 |
| 两跳邻域 | 17.0 → 14.8 | 49.4 → 57.7 | 359.3 → 58.8 |
| N 条记录的原子插入 | 74.8 → 75.0 | 266.4 → 171.7 | 2,246.0 → 1,203.7 |

另外测试了 N=1,000、10,000，避免用小样本的固定开销推断复杂度。N=10,000 的
结果如下，单位为 **CPU 毫秒**；倍数是前后 CPU 时间之比。

| 路径 | 优化前 | 优化后 | 倍数 |
|---|---:|---:|---:|
| 按来源取最新记录 | 1.193 | 0.0146 | 81.60× |
| 按重要性取前 10 条 | 2.294 | 0.040 | 57.33× |
| 混合召回 | 101.097 | 73.694 | 1.37× |
| 向量语义候选 | 1.892 | 0.962 | 1.97× |
| 两跳邻域 | 45.634 | 0.0583 | 782.60× |
| 10,000 条原子插入 | 550.995 | 458.416 | 1.20× |
| 显式提供实体的图写入流程 | 56.044 | 2.029 | 27.62× |

额外的稠密图测试在 N=100 时，混合召回从 126.394 ms 降到 19.429 ms，约 6.51×。
每次分配从约 65.3 MiB 降到 9.8 MiB。普通 N=10,000 混合召回的每次分配从约
75.7 MiB 降到 56.7 MiB；局部邻域从 23,987,320 字节降到 9,504 字节。
这些是累计分配量，不是进程峰值内存。

## 实施的优化与复杂度

- **有序数据库查询**：用活跃记录的时间、来源/时间、重要性/时间复合索引替换三个
  单列索引。匹配这些索引的有限查询从扫描候选并排序，变为约 `O(log N + K)`；
  全部活跃记录的时间排序读取从 `O(N log N)` 的排序成本降为线性索引遍历。
- **局部图遍历**：有限 BFS 只读取实际邻域，不再先加载全部 N 条记录和 E 条边。
  保留边的插入顺序、类型过滤、最大跳数、数量限制和删除过滤。无限遍历仍批量加载，
  避免把全图遍历变成逐节点 SQL 查询。
- **多路召回**：关键词与余弦相似度只计算一次，保存标量分数；同一请求的多个锚点
  共用邻接查询结果和已加载的记录。每个锚点仍有独立的 visited 集合及预算。
  假设 X 次图转移、d 维向量，重复余弦计算的主要成本由 `O((N+X)d)` 降为
  `O(Nd+X)`。缓存随请求结束，不跨命令保留过期状态。
- **语义候选与 Diff**：前 K 名选择由全量排序改为有界堆，选择成本从
  `O(M log M)` 降为 `O(M log K)`，选择存储从 `O(M)` 降为 `O(K)`。
  K=5 时，N=1/10/100/1,000/10,000 的比较次数实测为
  0/37/440/4,491/44,991；CI 检查操作次数上界，不以脆弱的计时阈值判定成功。
- **写入**：事务内按需预编译并复用记录/边插入语句，提交或回滚后释放。
  批量插入仍有 `O(B log(N+B))` 的索引工作，但不再为每行重复编译相同 SQL。
  显式提供实体时跳过无用途的全库实体提取。

固定查询与结果限额下，关键词检索仍随文本总量线性增长；精确向量扫描仍是
`O(Nd)`。保留策略刷新仍需聚合边、更新记录、排序候选，一般为 `O(E+N log N)`。
自动裁剪的活跃计数仍有 `O(N)` 成本。逐条精确比对的批量导入仍可能有
`O(BN+B²)` 的累计工作。这些路径没有被包装成“常数时间”。

## 取舍、测量与验证

测试使用 Apple M4、Go 1.25.4、单 P、真实临时 SQLite WAL 数据库和 128 维本地
合成向量，交替运行前后版本。记录实际耗时、进程 CPU 时间及分配量，共
108 个用例 × 5 轮 × 2 个版本。不调用付费模型，不计入 CLI 启动、网络和冷缓存。
机器是共享开发环境，所以这些数字是本机观测，不能直接作为线上延迟承诺。

小规模存在固定开销取舍：N=10 的局部 BFS 多约 8.3 µs；单条语义查询多约
1.6 µs。N=10,000 的未命中 LIKE 查询仍是线性扫描，本轮 CPU 约慢 4%。
这些结果均保留在报告中。更宽的索引最初增加了批量写入成本；加入事务内语句复用后，
最终 10,000 条插入的 CPU 比基线减少约 17%。
